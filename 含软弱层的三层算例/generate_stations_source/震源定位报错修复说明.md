# rank 591 震源定位越界：检查结果与修复

2026-11-14。本次仅在本地读取用户提供的两个 rank 591 数据库，并生成独立测试和补丁；没有修改用户 mesh、分区数据库或服务器文件。

## 已确认的证据

- 服务器 FORCESOLUTION 与新版文件 SHA256 一致，48048 个实际力源点全部满足外边界至少 100 m 净距。
- `proc000591_external_mesh.bin` 有 2365 个单元、160425 个 GLL 全局点。全部单元的八个角点严格构成有向 20 m 立方体，Hex8 映射为仿射映射，Jacobian 行列式恒为 1000 m³。
- 该分区坐标范围 X=3640–4000 m、Y=0–240 m；埋深范围为 220–460 m。用户另提供的 `proc000591_Database` 的节点范围与之相符。
- 用该分区数据库、实际源坐标与 SPECFEM3D v4.1.1 的 `locate_point.f90` / `recompute_jacobian.f90` 构造本地 Fortran 测试，原版在源 45278 触发邻接表越界。
- 该源 X=3724.148943549 m、Y=200 m、埋深=203.581721556 m。它在该分区上方约 16.42 m，进入定位程序的 20 m 分区扩展搜索范围。这是正常的候选分区搜索，不是源点越出整个模型。

## 越界如何产生

`find_best_neighbor` 进入循环时计算了 53 个邻居。循环内找到更好的单元后，`ispec_selected` 被更新为 2365；但下一次循环随之改读第 2365 个单元的邻居列表，而循环次数仍然沿用旧值。第 2365 个单元只有 40 个邻居。当循环读第 41 项时，访问数组第 218389 项，而数组长度只有 218388。

这可导致非法单元/节点索引、异常 Jacobian 或进程退出；具体表现受编译器和运行内存影响。本地加了显式越界检查，所以得到的是 STOP 99，而不是假装复现了服务器每一行报错。

修复只在本次邻居循环开始时保存列表起点，后续始终遍历这份固定列表。外层已有重定位循环，可以再围绕新的最佳单元继续搜索。

上游代码依据：https://github.com/SPECFEM/specfem3d/blob/v4.1.1/src/specfem3D/locate_point.f90

## 如何应用

将同目录的 `fix_specfem411_neighbor_search.py` 上传到服务器 SPECFEM3D 根目录，然后执行：

```bash
cd /share/SPECFEM3D_LYH/specfem3d-4.1.1
python3 fix_specfem411_neighbor_search.py --root . --apply
make -j4 xspecfem3D
```

脚本会自动备份 `src/specfem3D/locate_point.f90`。不带 `--apply` 时只显示差异。源文件与已核实的代码模式不匹配时会拒绝修改；已修复时不会重复修改。

必须确认编译成功，然后按原有 MPI/调度方式运行算例。启动的可执行文件应为重新编译的 `/share/SPECFEM3D_LYH/specfem3d-4.1.1/bin/xspecfem3D`；如果算例目录 `bin/xspecfem3D` 是旧的独立副本，需要使用新编译的文件。这个代码修改不要求重新划分网格或重建数据库，也不要求再修改源面几何。

## 验证范围

修复后本地测试检查全部 48048 个源：候选点进行定位，不在此分区搜索范围内的点按定位逻辑跳过，全部完成而未发生越界。补丁脚本通过预览不写文件、原件备份、重复执行、换行符和异常源码拒绝测试。

本地最近单元选择使用穷举最近中心代替 MPI 版本的 KD-tree，相等距离时可能选择不同候选。还没有完成服务器 600 进程运行，因而本地复现的源编号不等于已从服务器直接采集到的失败源编号。这是一处有直接复现证据的缺陷修复，最终仍需服务器复跑确认。
